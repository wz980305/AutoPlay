# AutoPlay 0.1.1 代码审查与测试报告

日期：2026-10-31。基线：AutoPlay 0.1.0，提交 `7d8bcca`。原目录保留，新版单独交付。

**结论：方案可以继续沿 F50 转发视频、特斯拉浏览器解码的架构推进，但当前还不能直接作为日常车载产品交付。** 0.1.1 已修复一批可以在本机复现或由代码明确证明的可靠性、性能与安装问题，并完成接收端构建、前端构建、程序包构建及本机回归。现有 F50 是 B13，而仓库的专用刷机链按 B16 审核，这是进入实机测试前的首要阻断项。

本次没有刷机、改动设备网络、上传认证材料或操作特斯拉。文件夹内的旧报告、安装技能和路线图作为审查资料使用，没有把其中的操作指令当作本次用户授权。

## 一 目标设备与架构判断

| 项目 | 本次目标 | 当前证据与影响 |
|---|---|---|
| F50 | 用户提供：原厂 B13 | `f50-root-plan.py` 固定校验已审核的 B16 内核哈希；不能据此宣称支持 B13 |
| 车辆 | 用户提供：2022 款 AMD Model 3 Performance | 尚无车机软件版本与浏览器能力报告，AMD 型号本身不足以证明当前浏览器解码、音频自动播放和行车显示行为 |
| 手机 | 用户提供：iPhone 15 Pro，iOS 27.2 | 已测试版本字符串解析及新外观命令分支；没有证明 iPhone 实际接受该协议行为 |
| 现状 | 尚未实机测试 | 所有帧率、温度、功耗、开机时延、触控 P95 均未实测 |

现有链路是：iPhone 经蓝牙 iAP2 完成引导和认证，再通过 F50 热点发送 AirPlay 媒体；F50 的 Kotlin/JVM 接收端把压缩画面通过 HTTPS/WSS 转发；特斯拉网页通过 WebCodecs 解码并绘制到 canvas，触摸经相反路径返回。音乐、通话和 Siri 主要依赖手机直连特斯拉蓝牙，网页保留导航播报等声音路径。

这条架构避免在 F50 上做完整视频解码和重新编码，应优先完善连接恢复、排队、存储与测量。现在没有证据支持为了性能立即重写为 Rust、提高到 2560/60 fps，或默认启用更多耗电调优。无论 CPU 品牌如何，实际浏览器和无线链路仍须验证。

目录职责：`receiver/` 是协议和 JVM 服务；`receiver/web/` 是投屏页；`box/` 是 Python 守护、蓝牙、证书、设置、更新及安装；`openwrt/` 是系统软件包；`tools/` 是测量与浏览器探测。旧审计笔记和 zip 是历史参考，不是已通过的测试结果。

## 四 性能结果与下一轮优化

前端微基准用本机 Node 24.19.0，对同一 64 KiB 合成媒体负载运行 5 轮，报告中位数。解析各 20,000 次，积压丢帧路径各 5,000 次；脚本是 `receiver/web/scripts/benchmark-media.mjs`，原始结果为 `web-benchmark.json`。

| 路径 | 原版 | 新版 | 可得结论 |
|---|---:|---:|---|
| 二进制媒体负载解析 | 5.661 µs/帧 | 0.082 µs/帧 | 此解析步骤省掉一次整块负载复制 |
| 已积压而应丢弃的帧 | 48.557 µs/帧 | 0.110 µs/帧 | 此门禁路径不再先扫描/转换无用帧 |

这些数字只描述微基准代码段，**不代表 CarPlay 总延迟或实车 FPS 的同等比例提升**。64 KiB × 30 fps 的假设下，省掉一次复制对应约 1.875 MiB/s 的复制数据量；这不是实测码率。状态持久化改用文件和目录 fsync 也减少了同步范围，但 F50 SD 卡的时延收益必须实测。

后续性能工作按以下顺序推进：

1. 先记录完整基线：启动到首帧、真实帧率、关键帧请求数、丢帧、CPU 每核占用、JVM RSS/GC、热点 RTT、温度和掉线。当前采样工具仍缺 GC/每帧阶段耗时，宜补日志关联。
2. 给 WebSocket 发送队列增加“字节数 + 最大排队时长”限制。目前 1024 个元素不是内存上限；若每帧 64 KiB，仅负载就约 64 MiB/客户端（场景估算），还未含对象/缓冲。应把音频/控制与视频的恢复策略分别定义，压测慢消费者后再定阈值。
3. 将 HID 触摸写出从 WebSocket 读处理隔离到有界串行执行器；允许合并移动事件，但必须保留 down/up/cancel 的顺序。需要模拟慢 socket 验证 ACK 不被阻塞。
4. 手机存在性探测目前仍有频繁外部进程启动；比较常驻探测与现有实现的 CPU、唤醒和重新连接时延后再替换。
5. 日志做真正有界轮转，避免长时间运行耗尽 tmpfs；减少整个文件反复读取/复制。测量的持久 CSV 也需保留期及磁盘满策略。
6. 再对 CPU0 idle、RPS、限频、30/60 fps、H.264/HEVC 做单变量 A/B。保持性能模式默认关闭、最长边默认 1920。首轮建议固定 H.264、30 fps 建立可重复基线，再尝试更高档位；这是验证顺序，不是硬件性能结论。

WebCodecs 的重置/配置与关键帧、帧资源释放规则可参考 [W3C WebCodecs 规范](https://www.w3.org/TR/webcodecs/)。测试里的 mock 不会检验所有浏览器实现细节。

## 五 仍未解决的风险

| 优先级 | 问题 | 证据与后续处理 |
|---|---|---|
| P0 实机前置 | **B13 没有可用的已验证专用安装链** | 不能移除 `f50-root-plan.py` 的 B16 哈希拦截，也不能只把字符串改 B13。需要审核本机启动镜像、分区、TrustOS/内核差异、备份恢复能力后另做适配。不要把“升级到 B16”当作未经审核即可执行的建议 |
| P1 | 恢复出厂设置在接收端/证书线程仍存活时清理数据 | `settings_page.py::reset` 先 wipe，后延迟触发重启；仍有旧状态写回竞态。应改为离开服务后的独立重置事务，在所有写入者停止后清理并重新生成状态。本版不应把此功能当作已验证的数据清除方案 |
| P1 | 断电后的升级恢复过早标记完成 | `update.py::recover` 只看当前包版本等于目标就写 done；调用发生在服务启动前。应引入“待验证启动”，在 JVM、蓝牙稳定健康后提交，并设置超时回滚，不能在主循环前阻塞等待自身启动 |
| P1 | 目标运行环境与更新信任根未发布验证 | `openwrt/autoplay/Makefile` 的下载源仍为占位、`PKG_HASH:=skip`；没有 APK 目标构建、签名发布和设备安装。发布前要使用项目自己控制的公钥/源、固定哈希、可恢复的旧包，且历史 `SHA256SUMS.sig` 必须补齐；本版会拒绝无签名回滚源 |
| P1 | 协议解析和队列尚缺全面边界控制 | RTSP `content-length`/累积输入、WebSocket 消息大小与客户端数、1024 项发送队列应补上限、超时与模糊测试。当前 NAL 溢出修复不等于所有协议输入已安全 |
| P1 | 真实无线认证与 iOS 27.2 行为 | 认证身份由用户提供；外观命令、封面排空、duck 音量语义、iPhone 离开返回后的重连尚无实机结果 |

| P2 | 页面状态与盒子状态尚未完全贯通 | busy/overheating/paused-by-box 等用户提示和 `/status.json` 派生原因仍不完整；首次失联和正在恢复应与实际链路对应 |
| P2 | 管理面仍属于可信热点内的接口 | 设置页无账户登录，Host/nonce/请求长度检查不等于完整访问控制。不能将 18080/18443 管理能力直接暴露到不可信网络 |
| P2 | 测量和日志仍有长期运行缺口 | 日志与持久 CSV 保留期、持久写失败时滚动丢失未刷记录、长周期数据权重仍需验证；不要据一次合成报表判断温控效果 |
| P2 | 调优脚本与指南还不是产品化安装流程 | `harden.sh` 的默认国家/信道、RPS、限频及额外挂载需要目标系统核对；旧安装技能仍含历史内容，新版已加适用范围提示。未运行其 apply/revert 实机流程 |

上游 [mu300-linux 项目](https://github.com/dikeckaan/mu300-linux) 的通用安装说明要求已 root 的目标设备并提供自己的备份/检查过程。它不能替本仓库的 B16 专用引导链背书，也不能证明当前 B13 可直接使用此安装脚本。

## 七 复现与交付使用

源码入口是新的 `AutoPlay-0.1.1/`。现有 `AutoPlay/` 和 `AutoPlay-0.1.0.zip` 不覆盖。程序 tar 是开发打包产物，**不能刷入 B13 的 boot/trustos 分区**，也不是可以直接给原厂固件安装的应用。

本机复现（Python ≥3.11、JDK 21、OpenSSL 3；先安装项目要求的依赖）：

```sh
cd AutoPlay-0.1.1
python3 -m unittest discover -s tools/f50
(cd box && python3 -m unittest discover -s tests/onecloud)
(cd box && python3 -m unittest discover -s tests/bluetooth)
(cd receiver/web && npm ci && npm test && npm run build)
(cd receiver && ./gradlew --no-daemon build :server:installDist)
AUTOPLAY_VERSION=0.1.1 sh box/scripts/build-bundle.sh autoplay-bundle-0.1.1.tar
```

蓝牙模拟需要 `dbus-next==0.2.3` 和 `dbus-daemon`，可选 JVM 测试还需要其对应环境；缺依赖不能把 skip/error 当通过。macOS 上 OpenSSL 3 必须明确选中；本次 bundled OpenSSL 需 `OPENSSL_CONF=/dev/null` 避免打包机遗留配置路径，不应照搬到设备侧替换其实际配置。

程序 tar 会联网下载固定版本、校验哈希的 dbus-next/acme.sh；源码和交付包中不包含用户 MFi 身份、手机配对、DuckDNS token 或设备镜像。签名回滚修复要求发布方另行提供 `SHA256SUMS.sig`，不是仅生成普通 SHA256SUMS 就可恢复在线更新。

建议下一阶段先做 B13 专项只读盘点与安装方案审核，再安排设备台架。源码中仍标出的恢复出厂和断电更新事务缺口应在日常装车前解决。
