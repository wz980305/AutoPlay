# 触摸到画面延迟：240 fps 手机慢动作测法

目的：测出"手指碰到车机玻璃 → CarPlay 画面出现变化"的端到端延迟，作为 WP0 的基线和每次改动前后的对比。路线图的目标是 **P50 ≤120ms、P95 ≤200ms**（《加固路线图》WP5），技术路径文档给的上限是 ≤150ms（目标）/ ≤200ms（阶段 1 验收）。目前公开的唯一数据是别的路由器代替热点测出的约 90ms；F50 自带热点上还没有人测过（1.0.0 在车上确认触摸可用，但没有量过延迟）。

这个方法只需要一部能拍 240 fps 慢动作的手机（iPhone 8 以后都行，设置 → 相机 → 录制慢动作 → 1080p 240 fps；多数安卓旗舰也有），不需要改任何代码。

## 原理

240 fps 的每一帧是 4.17ms。拍下手指和屏幕，数"指尖接触玻璃的那一帧"到"屏幕第一次出现对应变化的那一帧"之间隔了多少帧，乘以 4.17 就是延迟。误差来源是两端各 ±1 帧（±4ms）加上判断"第一次变化"的主观性（约 ±2 帧），单次约 ±15ms，所以要测多次取分位数而不是只报一个数。

链路上每一段都在这个数里：车机触摸采样 → 浏览器 pointer 事件 → WSS 到 F50 → F50 把 HID 报文加密发给 iPhone → iPhone 渲染 → H.264 编码 → Wi-Fi 到 F50 → F50 转发 → 浏览器解码 → canvas 绘制 → 车机屏幕刷新。相机法量的是驾驶者感受到的总和；分段定位要靠接收端和页面的计时（WheelPlay 的分段法，WP0），两者互补。

## 准备

- 车停好，CarPlay 画面正常显示。关掉车机的自动亮度，屏幕亮度调到中等，避免相机过曝看不清变化。
- 手机固定（小三脚架、杯架上垫东西，或者让副驾用两只手撑住手肘），镜头对准车机屏幕，**手指和屏幕都要在画面里**，距离 30–50cm。开慢动作 240 fps。
- 手指侧面入镜，让"接触瞬间"能从指腹变形或反光看出来。指甲涂一点亮色、或贴一小块白胶带，接触那一帧会更好认。
- 选一个**反馈最快、最明显**的操作对象。推荐按顺序：
  1. CarPlay 主屏幕的 App 图标：按下瞬间图标会变暗（高亮态），这是 iPhone 侧最快的反馈。
  2. 地图：单指拖动，画面开始跟手移动的那一帧。
  3. 音乐 App 的播放/暂停按钮。
  不要用会跳转页面的操作（动画有自己的延迟）。
- 记下这次测试的配置：F50 固件版本、AutoPlay 版本、信道/带宽、分辨率和帧率设置、增强模式开关（1.5.1 及以前叫「性能模式」）、CPU0 空闲状态、RPS 掩码、车机 Chromium 版本（探测页给的）、环境温度和 SoC 温度（measure.csv）。没有这些，数字无法对比。

## 步骤

1. 开始录像，等 2 秒。
2. 点一下目标（干脆地按下，不要犹豫着靠近），停 2 秒。
3. 重复 **至少 20 次**，每次间隔 2–3 秒；想看 P95 至少 30 次。中途不要动手机。
4. 停止录像。
5. 在手机相册里打开视频，把慢动作区间拉到覆盖整段（iPhone 相册 → 编辑 → 拖动底部的慢动作区间条），然后逐帧拖动（相册里细拖进度条就是逐帧；更省事的是导出后用桌面播放器的逐帧键，或者 `ffmpeg -i clip.mov -vf "showinfo" -f null -` 看帧号）。
6. 对每一次点击记两个帧号：
   - **T0**：指尖和玻璃第一次接触的那一帧（指腹开始压扁、或指尖和它在玻璃上的倒影合并）。
   - **T1**：屏幕上第一次出现对应变化的那一帧（图标开始变暗、地图开始位移）。
7. 延迟 = (T1 − T0) × 1000 / 240 ms。记进下面的表。
8. 排序后取第 50% 和第 95% 位置的值（20 次时 P95 取第 19 个，30 次时取第 29 个）。

小技巧：如果导出到电脑，`ffmpeg -i clip.mov -vf "select='gte(t,10)',showinfo" -frames:v 200 frames/%04d.png` 能把一段切成图片，用看图软件左右键翻，帧号就是文件名。

## 判读

| 结果 | 含义 | 下一步 |
|---|---|---|
| P50 ≤120ms 且 P95 ≤200ms | 达标 | 记录配置，作为后续改动的基线 |
| P50 正常、P95 很大（>300ms） | 偶发卡顿：多半是 CPU0 抖动（H3）、Wi-Fi 芯片休眠/ASPM（H8）或解码积压 | 对照 measure.csv 同一时刻的 CPU0 软中断%、中断增量；开 HUD 看解码队列；A/B `--cpu0-idle` |
| P50 高（>200ms）、分布紧 | 固定延迟大：分辨率/帧率设置、增强模式放大、浏览器解码慢（MCU2 Atom 单帧 60–100ms 级别） | 降分辨率、关增强模式、30fps 对 60fps 各测一次 |
| 漏点（按了没反应） | 触摸被丢。0.1.0 起页面已保证最短 30 ms 按压并在页面消失时补发抬起（`receiver/docs/TRIM-LOG.md`）；仍漏点则看 HID 发送链路（WP5 的另一半） | 换"按住 100ms 再抬起"的点法再测一次；两种结果都记 |
| 行车时明显变差 | 车机把页面节流了，或者 Wi-Fi 在行驶中掉档 | 用探测页的画布动画测试验证；检查"行驶中保持连接" |

## 要避免的错误

- 用 60 fps 或 120 fps 拍：分辨力只有 17ms/8ms，P50 的差异会被淹没。
- 手指从远处快速砸下：接触帧难判断，而且车机电容屏会在真正接触前就触发（悬停检测），系统性低估。
- 只点一次就下结论：单次误差 ±15ms，而且第一次点击常常带着 JIT 预热（开机后头一分钟最慢，H4）。开机后至少 3 分钟再测。
- 改了两个变量再测：分不清是谁的功劳。
- 忘了记 SoC 温度：热降频时的数据和常温数据不能放在一起比。

## 和其他测量的关系

- 盒子侧 `tools/f50/measure.sh` 在同一时间段记录 CPU0、温度、中断、TCP 重传，能解释 P95 的离群值。
- 接收端的 `TouchLatencyProbe`（WP0）已记录"触摸送出"（`AirPlaySession.onTouchSent`），但"回帧"一侧（`onFrame`）还没有调用者；接上它就能得到"页面收到触摸 → iPhone 回帧"的分段值，相机值减去它，就是车机侧（触摸采样 + 浏览器 + 显示）的开销。
- 探测页（`tools/probe/`）里的帧率和画布测试回答"行车时还刷不刷新"，不回答"快不快"；两者一起看。
